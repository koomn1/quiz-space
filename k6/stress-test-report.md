# تقرير Stress Test — Quiz Space

## النتيجة

تم إجراء اختبار ضغط متدرج باستخدام **k6 v2.2.0** على النشر `https://koomn1.github.io/quiz-space/`، وبطلبات `GET` فقط إلى app shell مع route labels لجميع المسارات المعروفة. لم يُنفّذ تسجيل دخول أو كتابة أو تعديل أو حذف بيانات.

الحد المستقر الذي ظهر في الاختبار هو **200 VU متزامن**. بدأ التدهور أثناء الانتقال من 200 إلى 400 VU، وأصبح واضحًا ومستمرًا عند مستوى 400 VU. عند هذه النقطة بدأت اتصالات GitHub Pages تُرجع `EOF` و`connection reset by peer` بدل استجابة HTTP ناجحة.

## التشغيل الكامل

في التشغيل المتدرج الأول، تم تنفيذ 25,507 طلبًا. نجح 22,887 طلبًا وفشل 2,620 طلبًا، أي نسبة فشل إجمالية قدرها 10.27%. أوقف k6 التصعيد تلقائيًا عند مرحلة 400 VU بعد تخطي حد الفشل المحدد.

في اختبار التأكيد المختصر المستقل، بدأ الحمل عند 200 VU ثم صعد إلى 400 VU. بقيت الاستجابات مستقرة في بداية مرحلة 200 VU، وظهرت أول رسائل `EOF` و`connection reset by peer` أثناء ramp إلى 400 VU. هذه النتيجة تؤكد أن نقطة التدهور العملية تقع قرب **400 VU**، مع هامش أمان تشغيلي يُفضّل أن يجعل حد الإنتاج أقل من ذلك.

بعد خفض الحمل، أُجري recovery smoke من 20 طلبًا متتاليًا؛ نجحت جميعها بحالة HTTP 200، بمتوسط 38.4ms. هذا يدل على أن الفشل كان throttling/connection saturation مؤقتًا أثناء الحمل وليس توقفًا دائمًا للخدمة.

## تفسير مهم

هذا الاختبار يقيس static app shell وطبقة HTTP/CDN فقط. التطبيق يستخدم hash routing، والجزء بعد `#` لا يصل إلى الخادم؛ لذلك تم اختبار كل route منطقيًا كـ label مع query مختلفة، لكن جميعها تعود إلى نفس app shell. لا يمكن اعتبار هذه النتيجة حدًا لقاعدة Supabase أو Cloudflare Worker أو تنفيذ React داخل المتصفح.

النتيجة الأقرب من الناحية التشغيلية هي أن GitHub Pages/CDN بدأ يرفض أو يعيد ضبط الاتصالات عند زيادة معدل الطلبات الناتج عن 400 VU. لا ينبغي تعميم الرقم على backend أو database قبل تشغيل اختبار منفصل على staging يرسل طلبات القراءة الحقيقية من Supabase وWorker.

## توصيات

يوصى باعتبار 200 VU حدًا مستقرًا مثبتًا لهذا السيناريو، ووضع سقف تشغيلي مؤقت بين 150 و200 VU إذا كان نفس نمط الزيارات المتزامنة متوقعًا. يجب تفعيل CDN/cache headers ومراقبة rate limits قبل رفع السقف.

يوصى بتشغيل اختبار browser-level منفصل على staging لقياس React وlazy chunks وLCP وطلبات API الفعلية، ثم اختبار Supabase وWorker ببيانات staging فقط. أما اختبار 400+ VU على الإنتاج فيجب عدم تكراره إلا داخل نافذة صيانة وبموافقة فريق البنية التحتية، لأن نتائجه أثبتت وجود connection resets.
